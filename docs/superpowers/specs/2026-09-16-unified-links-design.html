Bounded and Unbounded

One gg:// link spelling for everything gg can show, and one rule for comparing any two of them.

branch feat/unified-links commit c4f04a6c status agreed 4 plans

01 The problem

Links address a file, a line, a hunk, a commit or a merge preview. Three things a user looks at cannot be linked at all — bookmarks, shelf entries and branches — and no link can be compared against another.

Comparison lives in per-surface menus instead. gg compare accepts a second, ad-hoc spelling (bookmark:<id>, shelf:<id>, @staged, @worktree), and the pair-compare flows are menu-driven selections that only work within one entry kind.

  • An agent cannot be handed “this shelf entry” or “this branch” by reference — the CLI and MCP have no spelling for them.
  • Comparing across kinds needs a new menu per pair, so most pairs simply do not exist.
  • The pairing rules live in internal/cli/compare.go:93-95, so the TUI, web and MCP each answer the same question differently, or not at all.

02 The model

A pair is bounded. A point is unbounded.

Every link, once resolved, evaluates to a file set of one of two kinds. Which kind it is follows from the link’s shape alone — nothing is guessed, and nothing depends on the other side of a comparison.

unbounded

Every file in the repository at some state.

  • a commit tree
  • a branch or tag tip
  • the working tree
  • the index

bounded

A finite, enumerated set of paths.

  • a merge preview’s files
  • a shelf entry’s members
  • a single file
  • a bookmark

A commit is a point, so gg://repo@abc123 is the tree at that commit. To address what a commit changed, spell the pair.

Grammar

gg://<repo>[/<path>][@<target>][:<line>|#<hunk>][?<hint>]
targetkindstatus
(absent) — working treeunboundedshipped
stagedunboundedshipped
<sha> — 7..64 hexunboundedshipped
ref:<name> — a branch or tag tipunboundednew
<a>...<b> — merge previewboundedshipped
<a>..<b> — two-dot change-setboundednew
any of the above with a /<path>bounded, one elementshipped

Separator safety

Every new separator was checked against git check-ref-format, because a branch name rides inside the preview pair and the ref: form:

charlegal in a refname?consequence
:noref:<name> and the :<line> suffix are both unambiguous
^ ~nofree for future revision operators
?nosafe as the hint separator — a refname can never reach it
@ # =yesalready rejected by the shipped model.LinkRefOK

No shorthand for “this commit’s change.” A producer copying from a commit diff view resolves the first parent at copy time and emits the explicit pair @abc122..abc123.

That keeps the link portable and self-describing, and adds exactly one grammar form rather than a ^!-style operator that would fight zsh history expansion on the CLI. For a merge commit the producer takes the first parent — recorded in the link, so the choice is visible rather than implicit.

The hint — ?<hint>

?bookmark=<id> and ?shelf=<id> record which surface the link was copied from. The address is the identity; the hint is where to open it — an HTML anchor, not a different address.

  1. Compare ignores the hint. A bookmarked commit and the same commit picked off the log are one endpoint. No bookmark×shelf×commit matrix.
  2. Navigate honours it. Same address, different landing: reveal the bookmark row, the shelf row, or the commit in the log.
  3. It degrades; it never fails. On another machine the address still resolves and the hint is dropped with a notice.

One exception, and it is the only machine-local link in the system — the hint carries content when there is no address:

shelf entrylinkcontent comes from
shelved commitgg://repo@abc123?shelf=<id>the commit while it resolves; the frozen tar once it is gc’d
shelved filegg://repo?shelf=<id>the hint — those bytes were never in git

The first row is exactly the hybrid semantics domain.ResolveCommitEntryEndpoint already implements. Bookmarks need no such form: a model.Bookmark is a stored FileAddress, so its link is the address it points at. Merge previews keep their shipped spelling, carrying the branch-name pair deliberately so it travels.

Stashes

A stash is a commit, so it needs no new grammar. internal/git/stash.go already says so — StashCommit “resolves a stash ref to its commit SHA so the file tree / diff can read it as an ordinary commit.”

linkkindmeaning
@<stash-sha>unboundedthe tree the stash captured
@<stash-sha>^..<stash-sha>boundedwhat the stash changes

The first-parent rule above is already correct here by construction: a stash’s first parent is the HEAD it was made on, which is exactly what git stash show diffs against. Two rules are specific to stashes:

  1. stash@{N} must never appear in a link. It is positional — pushing, popping or dropping any stash shifts every N, so the same link text would silently name a different stash. The producer resolves to the sha at copy time. ?stash=<n> survives only as a landing hint, and it is the most fragile hint in the system: N changes while the thing it names does not.
  2. A stash link can dangle, with no fallback. A stash commit is reachable only through refs/stash and its reflog. Unlike a shelved commit there is no frozen tar, so a popped or dropped stash is a plain CommitGoneError — and the message should point at shelving as the way to keep it.

Untracked files are included. StashPush takes includeUntracked, so gg can create three-parent stashes — [HEAD, index, untracked-tree] — whose untracked files live in the third parent, not in the stash’s own tree. A plain ^.. would silently omit them.

The bounded set is therefore tracked changes plus parent 3’s files, entering as additions. This is deliberately not git stash show — it is “what I stashed”, which is the user’s mental model, and gg already knows which it is because StashPush recorded the flag.

03 The algebra

unbounded × unbounded  →  BOUNDED   git diff A B: the differing paths
bounded   × bounded    →  BOUNDED   symmetric over the union of member paths;
                                 present in one only ⇒ A / D
unbounded × bounded    →  BOUNDED   project the tree onto the bounded side's
                                 paths; a key absent from the tree ⇒ A / D

The asymmetry is load-bearing: you can only ever scale down. Growing the bounded side to the tree’s size would mean comparing one file against every file in the repository. So the bounded side always supplies the key set.

Compare is closed — every comparison yields a bounded set. That makes a compare result the same kind as a merge preview, so it is saveable, linkable, and usable as an endpoint of the next comparison. This is what makes “compare everything with everything” terminate.

domain.shelfCommitCompare is already the third row, with a shelfIsRight direction flag. The work is generalizing that one function — not inventing a lane.

Worked examples

leftrightlaneresult
@abc123@def456u × ugit diff abc123 def456
@main...feat/x@main...fix/yb × bwhich paths each branch touched, and how they differ
/parser.go@abc123@def456b × uparser.go at each; absent in def456 ⇒ D
?shelf=<id>@abc123b × uthe shelf’s members, projected onto the tree
@ref:mine@ref:theirsu × uthe two tips
@abc122..abc123?shelf=<id>b × bdid the shelf hold the same change as the commit?
@<stash>^..<stash>@ref:feat/xb × uis my stash already on the branch?
@B...A@E...Db × btwo branches, each bounded against its own base — did they change the same files, the same way?

04 Architecture

Validity is a property of the type, not a checklist

Parse, don’t validate. There are exactly two funnels in this design, and after each one the value in hand carries its own guarantee. Nothing downstream re-checks, because nothing downstream can hold an invalid value.

funnelproducesguarantees
model.ParseLink(s)a Linkthe grammar above, including LinkRefOK / LinkPathOK
a model.*Endpoint(…) constructoran Endpointthe kind’s field invariants, and its boundedness

Three traps in the shipped type make this mandatory rather than stylistic. All three were verified against the tree before this section was written:

  1. 54 raw model.Endpoint{…} literals exist outside tests. Three new kinds means 54 sites that might have to care.
  2. The zero value is silently valid. EndpointWorkTree = iota is 0, so model.Endpoint{} is a working-tree endpoint — and internal/cli/compare.go returns exactly that on its error paths.
  3. default: already means “commit”. In FileRef, Display and CacheTag the switch falls through to the commit case, so adding EndpointRef with no other change would silently yield FileRef{Source: SourceCommit, Locator: ""} — a wrong answer, no error, in three methods.

Endpoint is never serialized — session_snapshot.go converts through its own snapEndpoint wire type — so unexported fields cost nothing.

type Endpoint struct {
    kind     EndpointKind // unexported: the only way in is a constructor
    hash, ref, shelfID string
    a, b     string
    threeDot bool
    bounded  bool // computed ONCE at construction, never re-derived
}

func WorkTreeEndpoint() Endpoint
func CommitEndpoint(hash string) (Endpoint, error)  // 7..64 hex
func RefEndpoint(name string) (Endpoint, error)     // LinkRefOK
func ShelfEndpoint(id string) (Endpoint, error)
func PairEndpoint(a, b string, threeDot bool) (Endpoint, error)

func (e Endpoint) Bounded() bool // reads the field; nobody re-derives

Four rules follow, and they are the whole of the enforcement:

  • EndpointInvalid = iota comes first, shifting EndpointWorkTree to 1. Endpoint{} becomes unusable and every error return is obviously wrong instead of plausibly right.
  • Every switch gets a panicking default: naming the kind, replacing the three silent commit fall-throughs.
  • Boundedness is stored, not computed by callers — the rule is applied exactly once, in the constructors.
  • One table test enumerates every kind, asserting a constructor, Bounded(), FileRef, CacheTag and Display. A kind added without a row fails the build. That is the single place the rules are checked.

Rejected alternative: a closed interface with real variant types (CommitEnd, PairEnd, …). A stronger guarantee — but Go does not exhaustiveness-check type switches, so it still needs the same table test, while reshaping all 54 sites plus Differ, CompareFiles, MCP and the TUI rather than respelling them.

No new address type

gg already has five address-ish types — model.Link, FileAddress, FileRef, Endpoint, Bookmark. This design adds none. Endpoint is already “one side of a whole-tree comparison”; it gains two kinds — EndpointRef (a branch/tag tip, unbounded) and EndpointPair (A..B or A...B, bounded) — behind the constructors above.

The one pipeline becomes Link → Resolved → Endpoint → FileSet → CompareSets, driven by two new domain functions:

func (s *Service) EvalEndpoint(ctx, e model.Endpoint) (FileSet, error)
func (s *Service) CompareSets(ctx, left, right FileSet) ([]model.CommitFile, error)

domain/compare_entries.go shrinks to thin adapters, and the ad-hoc pairing rules in internal/cli/compare.go move into domain — so all four frontends share one answer.

Two new packages

Both are DAG leaves owned by domain; frontends never import them, per the notes / shelf / preview convention.

packagecontentsprecedent
internal/linkhistthe 20-entry MRU of created links: {Link, Desc, Created}, TOML + O_EXCL lock under XDG stateinternal/notes
internal/savedcompare{Left, Right *Link, Label} — absorbs merge previewsinternal/preview

Not named clipboard — that package already exists (the OS clipboard writer). Every “copy gg link” action on any surface appends to linkhist; re-copying an identical link moves it to the top. Desc is stored at creation, because the describing context is gone by read time:

branch:   feat/x            gg://gigagit@ref:feat/x
bookmark: auth fix          gg://gigagit@abc123?bookmark=auth-fix
shelf:    WIP parser        gg://gigagit@abc123?shelf=commit-x-9f3a1
preview:  main...feat/x     gg://gigagit@main...feat/x
commit:   abc123 fix auth   gg://gigagit@abc123
stash:    WIP on main       gg://gigagit@9c1f2a3^..9c1f2a3?stash=0

The stash row shows why Desc must be captured at creation: stash@{0} is gone from the link by design, and the subject is the only thing that makes the row recognizable in the list.

Merge previews fold in — and the data is discarded

A saved comparison and a merge preview are the same kind, but not the same shape: MergePreview{Source,Target} is one side, and preview notes anchor on its source tip. So the store holds both shapes explicitly:

type Entry struct {
    Left  model.Link
    Right *model.Link // nil ⇒ a saved SET (a merge preview), not a pair
    Label string
}

Framework gap to build. preflight.StoreProbe → verdict → consent prose → engine.ApplyMigration is exactly the right machinery, and StoreVersions 1→2 is the precedent.

But ApplyMigration today only deletes git refs and stamps via Repo.StampStoreFormat — the only registered store is ref-backed. previews.toml is a machine-local XDG file store, so the op needs a file-backed discard action alongside Refs. Small and clean, but new work, not free reuse.

05 Surfaces

One rule makes the compare dialog useful: every “copy gg link” click, on any surface, appends to the history.

Bounding a side in the compare dialog

Shared by the TUI and web dialogs. A branch link is unbounded because no base can be guessed — but the dialog can ask, which puts the choice in front of the user instead of in the resolver.

┌─ link comparison ──────────────────────────────────────────┐
│                                                            │
│  [ link 1 — branch A / file / commit / whatever         ]  │
│      [ base — branch B ]   shown only when link 1 is a      │
│                            branch; the set becomes every    │
│                            file a merge preview of A into   │
│                            B would change                   │
│                                                            │
│  [ link 2 — branch D / file / commit / whatever         ]  │
│      [ base — branch E ]   likewise for link 2              │
│                                                            │
└────────────────────────────────────────────────────────────┘

Each side carries its own, independent base row — and that independence is the point. Bounding both sides turns branch↔branch from “compare two tips” into “did these two branches change the same files, the same way”: a bounded × bounded comparison the bare branch link could not express, reached without any grammar change.

Direction. In gg’s preview vocabulary PreviewAdd(source, target) renders merge-base(target, source)..source, spelled @target...source. So the selected link is the source and the base is the target: choosing base B for branch A rewrites the field to @B...A.

Bounding is a link rewrite in the field, not dialog-only state. Choosing base main for @ref:feat/x rewrites that field to @main...feat/x.

The field always holds a real link, so a saved comparison, its CLI equivalent and the history entry are byte-identical. There is no hidden dialog mode that a gg compare invocation could not express.

Three-dot, matching previews exactly — internal/cli/preview.go documents the semantics as merge-base(target, source)..source, and PreviewSummary already exposes the base it used. So a branch bounded in the dialog and a saved preview of the same pair are the same set.

Bounding generalizes to any point. It is just “pick a second point to make a pair”:

unbounded sidethe picker offersrewritten to
branch / tag tipits upstream, else the trunk — preselected, visible, changeable@base...branch
commitits first parent@parent..sha
working tree / indexnothing — no base existsno affordance shown

Offered, never required. Leaving both sides unbounded compares the two tips, which is the agreed meaning of branch↔branch. The affordance never blocks the dialog and never rewrites a field the user did not touch.

New machinery, flagged honestly. gg has no default-base notion today — PreviewAdd(ctx, source, target, label) always takes both names, and nothing infers one. The suggestion order is therefore new, and it is a preselected suggestion in a picker, never a silent default: the “never guess” rule holds because the user sees and confirms the base before the rewrite. The CLI stays explicit — no --base inference; an agent spells the pair.

TUI

  • Copy-link rows via the existing . type-to-filter menu, on branch / commit / bookmark / shelf / preview / stash rows. A commit row copies the tree; a commit diff view copies the pair. A stash row copies the pair — what the stash changes — and always the resolved sha, never stash@{N}.
  • The # paste prompt gains a history picker alongside free paste.
  • New palette command “Compare with link…” — two fields, each filled by paste or from the 20-row history, then the compare view, then Save comparison.
  • Bookmark↔shelf compare moves from menu-selection to links; bookmark↔bookmark and shelf↔shelf keep their existing menus.

CLI — the agent surface

gg link <what>               emit a link for a branch/commit/bookmark/shelf/preview
gg links                     the 20-row history, terse
gg compare <left> [<right>]  links are the primary spelling; today's
                             bookmark:<id> / shelf:<id> / @staged / @worktree
                             keep working, mapped onto links
gg compare --save <label>    store the bounded result
gg open <link>               navigate (grows ref: and ?hint)

MCP & web

MCP gains gg_link_resolve, gg_link_list and gg_compare_links; gg_compare_file grows link arguments. Then an agentskill.Version bump and gg init --update.

Web carries the same copy rows and dialog, but the history must be served over /api/linkhist, never browser storage — gg web binds a random port each run, which empties localStorage.

06 Testing

  • Endpoint exhaustiveness — one row per kind, asserting a constructor, Bounded(), FileRef, CacheTag and Display; a kind added without a row fails the build. Plus every constructor rejecting its bad inputs, and Endpoint{} being invalid.
  • model — table-driven String(ParseLink(s)) == s over every new form; reject cases for refnames containing @/# and paths containing ?.
  • domain — the algebra as an explicit kind×kind matrix against a real git repo in t.TempDir(). This is the test that earns the design: every cell asserted, including projection direction — whether a missing key reads A or D depends on which side is bounded.
  • stashes — a three-parent stash (gg stash -u) whose bounded set must include the untracked file from parent 3; and a popped stash whose link yields CommitGoneError rather than a wrong answer.
  • e2e — gg link → gg compare → gg compare --save round-trips as TOML scenarios.
  • web — links.js pinned against the Go grammar, as the JS date port is pinned by model.CommitDateLayout.
  • i18n — the four AST gates.
  • migration — format 1→2 discards previews.toml and stamps, only after consent.

08 Out of scope

GitHub PR read/write via gh

Agreed as a separate project. It shares no machinery with this spine: a new external binary, a remote read/write lane, a review-state model, and a capability detector closer to exttool/agentinit than to preflight. It gets its own brainstorm once this ships.

Cross-repository comparison

Nothing in the algebra stops gg compare gg://repoA@abc gg://repoB@def — both sides evaluate to file sets, and the sets do not care which repository produced them.

What stops it is reservation: every read goes through one domain.Service under one repogate reservation, so a cross-repo compare needs two services and two reservations acquired in a fixed order to avoid deadlock. Refused in phase 1 with an explicit message, and revisited once workspace groups land — that roadmap item already needs multi-repo reservation ordering for parallel background-pull. Same problem, solved once.
